# H-050 — Head-to-head: does /agent-spec-raw-code-full pay for itself?

## Local part (done 2026-11-18)

`bin/agent-spec-bench.py --skill agent-spec-raw-code-full`: the six `agent-bench.jsonl`
questions, the same local model (`ollama:qwen2.5-coder:7b`), the harness on in both arms; the
skill arm opens the prompt with `/agent-spec-raw-code-full`, and the local agent loads the
installed `SKILL.md` into the system prompt the way Cursor attaches a skill. Token counts are
Ollama's `prompt_eval_count`, summed over every model call, so the skill's re-send is measured.

| Run | Skill size | Arm | Correct | Input tokens | Tool calls | Time |
|---|---|---|---|---|---|---|
| 20261118T205801-df2203 | 3,848 B | plain | 3/6 | 24,920 | 17 | 42 s |
| | | skill | 3/6 | 41,139 (+65%) | 13 | 32 s |
| 20261118T210008-fa3fba | 2,541 B | plain | 3/6 | 24,920 | 17 | 36 s |
| | | skill | 2/6 | 39,989 (+60%) | 15 | 33 s |

Findings:

- On short single-request questions the skill is pure cost: its text is re-sent on every model
  call (about 2,500 extra input tokens per question), and there is nothing for it to save,
  because the local agent's Read already returns at most 80 lines.
- 75% of the skill restated the always-on rule (`CURSOR.md`, installed as
  `.cursor/rules/agent-spec.mdc`). It now carries only what that rule does not: preflight,
  optional `rg`, prefix stability, reply shape, Complexity Override. 3,848 B to 2,541 B.
- Accuracy is the same within noise (one question in six flipped between runs).
- n = 6: a smoke test, not a benchmark.

The dashboard shows the latest run on **Impact › Summary** ("Measured: does
/agent-spec-raw-code-full pay for itself?"), each arm linked to its request trace.

## Owed

The Cursor half: the same three tasks in plain Cursor and with `/agent-spec-raw-code-full`, on
the H-010 mesh, where Read is not capped and long sessions re-send what the skill keeps out.
Blocked on Cursor usage (the plan is exhausted).

2026-11-19: `bin/agent-spec-cursor-bench.py` runs that half on any machine whose Cursor plan can
run `cursor-agent -p`. It sends the 3 multi-turn tasks in `evals/cursor-bench.jsonl` (4 turns
each, one resumed chat per task) plain and with the skill, and records Cursor's own `usage` per
turn. Steps are in `docs/LIVE-TESTING.md`. This machine cannot run it: the Free plan cannot pick
a custom model, and every `cursor-agent` prompt here hits the usage limit. Tested against a fake
`cursor-agent` (`tests/test_cursor_bench.py`); not yet run against real Cursor.

2026-11-19: the same script runs without Cursor via `--agent local --model groq:<model>`. The
local agent gained a Groq mode (OpenAI-compatible API, opt-in through
AGENT_SPEC_ALLOW_REMOTE_MODELS=1, key from GROQ_API_KEY or `~/.config/agent-spec/groq_api_key`,
429 waits, Groq keys redacted). Tested against a fake Groq endpoint (`tests/test_groq_agent.py`).
These numbers are labelled "Not Cursor" and do not close the Cursor half.

2026-11-19, first live Groq run (`groq:openai/gpt-oss-120b`, run `20261119T103117-f326f8`). Groq's
free tier caps this model at 200,000 tokens per day, and the run hit that cap after 15 of 48
turns. Only 7 turns have measured usage in both arms (savings, all 4 turns; hooks-risk, turns 1-3;
one repeat each). On those 7 paired turns:

| Metric | Plain | Skill | Change |
|---|---|---|---|
| Correct | 3/7 | 2/7 | |
| Input, uncached | 47,876 | 55,299 | +16% |
| Cache read | 3,840 | 14,336 | +273% |
| All input | 51,716 | 69,635 | +35% |
| Output | 5,123 | 7,027 | +37% |
| Tool calls | 26 | 26 | 0% |

Skill input was higher on 6 of the 7 turns, and tool calls did not drop. In this agent the
skill's ~650 tokens are re-sent at every step (about 5 steps per turn), and nothing it asks for
shrinks a step. n = 2 chats per arm: a smoke test. Accuracy is low in both arms (5/14), and two
plain turns ran out of tool steps; the agent, not the skill, limits the answers. A complete run
needs about 380,000 tokens, roughly two days of the free quota on this model.

Skill input was higher on all 12 turns, and on every task (+58% to +85%). The three skill misses

reduce tokens in this agent on any task. Short multi-turn chats on read-only questions are not
where its rules (fewer turns, capped tool output) have room to act, and the ~650 tokens it adds
are re-sent at every step.
