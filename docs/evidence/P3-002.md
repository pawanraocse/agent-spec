# P3-002 evidence (2026-11-13, steps 1–3 of 3)

The design is the LLD addendum in `docs/IMPLEMENTATION-GUIDE.md` ("LLD addendum — P3-002 step 1").

## Why this step comes first

A probe of 10 local repositories (names withheld: this repository must not name others)
found no real cross-repo HTTP or message links. It also showed that the extractor could not
see the HTTP surface of JAX-RS or servlet services at all: 0 endpoints in two Java
repositories that have 174 `@Path` files and 515 servlet files between them. Matching across
repositories cannot work until both sides of a call are in the graph.

## Built

- `extract_routes` in `bin/graphify-build.py`. Graph 5.2 adds `routes: ["<VERB> <path>"]` to
  each node, and `endpoints` stays the distinct paths for existing consumers.
  - Annotation runs join class prefixes to member paths for JAX-RS, Spring, Micronaut and
    NestJS, and read `@WebServlet`.
  - Flask/FastAPI, Express and Go keep line patterns, which now carry the verb.
  - `web.xml` mappings attach to the servlet-class file by exact FQN; unknown or ambiguous
    classes are skipped.
- `calls` recognises `@RegisterRestClient(configKey = ...)`. `HttpClient`, `ClientBuilder`,
  `HttpURLConnection` and OkHttp count as dynamic callers.
- `graphify-cli.py endpoints` prints routes with their verbs.
- `PARSER_VERSION` is 5.2, so caches re-parse once.

## Verified

- `python3 -m unittest tests.test_graph_signals`: 12 OK. The cases cover JAX-RS (with and
  without the `ws.rs` namespace), Spring prefixes, arrays and `RequestMethod`, a Spring
  `@Controller` bean name not being taken as a prefix, Micronaut, NestJS, servlets, the
  function frameworks, REST-client targets, Java dynamic clients, and a `web.xml` build.
- Regression: the graph, mesh, symbol, ingest, blast-radius and API suites pass, and
  `bin/agent-spec-selftest.sh` ends with "All selftests passed.".
- Real repositories, built with `--out` into a scratch directory:

  | Repository | Endpoints before → after | Files with endpoints | Verbs found |
  |---|---|---|---|
  | Java/Quarkus service | 0 → 347 | 0 → 112 | GET 124, POST 191, PUT 36, DELETE 21 |
  | Java servlet/JAX-RS server | 0 → 173 | 0 → 102 | GET 105, ANY 48, POST 25, PUT 15, DELETE 12, HEAD 2 |
  | Spring Boot service | 100 → 82 | 33 → 33 | 0 endpoints lost |

  For the Spring service, the drop from 100 to 82 is de-duplication only: the class prefix and
  the method path used to count separately. In the servlet server, 63 of 81 `web.xml`
  mappings resolve. The other 18 have no `<servlet-class>` (JSP-backed) or name a library
  servlet.

## Step 2: structured outbound calls

The design is the LLD addendum "P3-002 step 2" in `docs/IMPLEMENTATION-GUIDE.md`.

- Graph 5.3 adds `http_calls: [{verb, target, path, via}]` to each node. The `via` values are
  `url`, `feign`, `rest-client` and `fetch`. Legacy `calls` strings still feed in-repo
  `http` wiring.
- **Bug fixed from step 1:** a `@FeignClient` or `@RegisterRestClient` interface is now read
  as a client. Its mappings become calls aimed at the client's target, and they are no
  longer counted as served routes. In the Java/Quarkus service, 31 rest-client methods
  moved, so routes went from 372 to 341.
- **Noise gate:** a URL literal counts as a call only in a file that makes HTTP calls. XML
  namespaces, schema ids and doc links were most of the earlier volume.
- `PARSER_VERSION` is 5.3.1. Any extractor change must bump it, because the cache is keyed
  by it; one stale measurement during this step came from not bumping it.

| Repository | `http_calls` before gate → after | Top targets after |
|---|---|---|
| Java/Quarkus service | 278 → 103 (url 58, rest-client 31, fetch 14) | internal services such as an AI service and an asset server |
| Java servlet/JAX-RS server | 306 → 34 | mostly third-party (OpenID, Google APIs) |
| Spring Boot service A | 96 → 6 | its own auth service, a payment provider |
| Spring Boot service B | 35 → 7 | its own platform service |

Verification: `tests.test_graph_signals` gives 19 OK (Feign name, url and placeholder
targets; MicroProfile `configKey` with an `@Path` prefix; the verb on the line or an explicit
`HttpMethod.X`; requests, fetch and axios; the cap; the noise gate). `bin/agent-spec-selftest.sh`
ends with "All selftests passed.".

## Step 3: cross-repo matching and mesh query

The design is the LLD addendum "P3-002 step 3" in `docs/IMPLEMENTATION-GUIDE.md`.

- `graphify-mesh.py build` adds cross-repo `http` edges (service identity first, then path
  against the owner's routes, then a route that is a suffix of the call path) and `message`
  edges (the same topic string). A known service with no matching route gives a repo-level
  `http` edge with `resolution: "service"`. Path-only matches, for relative and unaliased
  `config:` targets, are only ever `http_ambiguous`. Loopback and third-party hosts never match.
- Identity is the repo id, the member's service names, and the hub's optional
  `.agent-spec/mesh-aliases.json`. Only Kubernetes `*.svc` hosts are shortened to their first label.
- Member graphs older than 5.3 are listed as stale, and `build` says to run `--refresh`.
- `stats` counts the confident types (`imports`, `http`, `message`) and reports `by_type`.
- `graphify-mesh.py query --file <repo_id>:<path> [--depth N] [--json]` prints the outgoing and
  incoming cross-repo edges, then the cross-repo blast radius over confident edges only.
- The `agent-spec-query-graph` skill tells the agent to run `query` and to report every
  `*_ambiguous` edge as unresolved.

### Verified

- `python3 -m unittest tests.test_graph_mesh`: 15 OK, 8 of them new. They cover a Feign client
  matched to a Spring route by service name, a repo-level edge for an unknown handler, an alias,
  a Kubernetes host, a gateway prefix, loopback and third-party hosts yielding nothing, a Kafka
  topic across repos, a relative `fetch` that is only ambiguous and needs two literal segments,
  stats by type, a depth-2 blast radius (a client, then a file that imports it), and the path rules.
  The P3-001 tests now clean up their temporary directories.
- `tests.test_graph_signals` passes, and `bin/agent-spec-selftest.sh` ends with "All selftests passed.".
- The same 10 local repositories as P3-001, rebuilt with `build --refresh` in 26 s: every member
  is graph 5.3, and there are **0 cross-repo edges of any type**, ambiguous included. Every call
  target was accounted for:

  | Calls | Why no edge |
  |---|---|
  | `localhost` / `127.0.0.1` in 7 repos | loopback never matches |
  | third-party hosts (exchanges, OpenID, Google APIs, doc sites) | not a mesh identity |
  | `auth-service` in one repo, `platform-service` in another | a service of the caller's own repo; five template-derived repos each have an `auth-service` |
  | 14 relative `fetch` calls in the Java/Quarkus service's frontend (6 paths under `/api/`) | no repo serves them |

  The repositories do not call one another, so 0 is the correct answer, as it was for imports in
  P3-001. The 14 relative calls most likely go to the frontend's own file-system API routes,
  which the extractor does not model. That is a route-coverage follow-up, not a matching defect.
