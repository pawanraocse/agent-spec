# P3-001 evidence (2026-11-13, partial)

The design is the LLD addendum in `docs/IMPLEMENTATION-GUIDE.md` ("LLD addendum — P3-001").

## Built

- `bin/graphify-mesh.py add | remove | build [--refresh] | stats [--json]`. The hub keeps
  `.agent-spec/mesh.json` (`{repo_id, path, graph_sha, updated}`) and one graph per member
  under `.agent-spec/mesh/<repo_id>/`. The merged graph goes to
  `.agent-spec/graph/mesh-graph.json`, with node ids of the form `<repo_id>:<path>`.
- `graphify-build.py --out DIR` builds a member's graph without writing to the member repo.
  Graph 5.1 adds `unresolved_imports`. It skips platform namespaces, file names such as
  `AtlBase.h`, wildcards, and tokens with fewer than two segments.
- A cross-repo edge forms only on an exact qualified name. For Java and Kotlin that is the
  FQN after the first source root; for Python it is the module path from the topmost
  package. A name defined in two or more repos becomes `imports_ambiguous`.
- `install.sh` ships `graphify-mesh.py`. The `agent-spec-query-graph` skill explains how to
  read the mesh, so cross-repo questions stay a skill's job.

## Precision on the H-010 fixture (2026-11-18)

`examples/mesh-demo` (4 repos: shared Python library, Flask-style API publishing a topic,
worker consuming it, JS UI calling the API). `tests/test_mesh_demo.py` compares every
cross-repo edge against the fixture's ground truth: 6 edges, 4 distinct (source, target, type)
pairs, all correct and none missing — precision 100%, recall 100% on the fixture. A real pair
of services is still to be measured before this row closes.

- 2026-11-18 [x] **Real services.** The modules of the cloud-infra-lite template (`common-dto`, `common-infra`, `auth-service`, `backend-service`, `gateway-service`, `frontend`) were added as six mesh members to a scratch hub with `graphify-mesh.py add <path> --id <module>`. The hub only reads its members. Result: 230 nodes and 29 cross-repo `imports` edges (auth-service→common-dto 10, auth-service→common-infra 3, backend-service→common-dto 5, backend-service→common-infra 5, common-infra→common-dto 6). `examples/mesh-demo/measure_imports.py HUB ROOT` compares them with every Java `import` that names a class file in another member: 29 found, 29 in the ground truth, 29 correct, so **precision 100%** and **recall 100%** for imports. This is above the 75% bar in MASTER-PLAN. Earlier on the H-010 fixture, all 6 edges were correct and none missing.
- Limitation, measured and not hidden: the mesh drew no HTTP edge from `frontend` to the services. The Angular client builds URLs from `environment.apiUrl` plus a relative path in `base-api.service.ts`, so the graph sees only `localhost /`. The gateway routes are Spring Cloud Gateway configuration, not code. There are no false HTTP edges, so precision is unaffected; HTTP recall on this pair is 0. Static HTTP matching works only where the call site carries a literal path, as it does in the H-010 fixture.
